# Security

The repository is public and MIT licensed; the deployed CRM and account service are private. Never commit real customer records, credentials, tokens, subjects or email addresses of real people. Keep deployment credentials in the approved platform configuration.

### Anthus One hosting

`one.anth.us` is a public static site, so it holds no data: its bucket contains only the built portal bundle. The bucket blocks all public access, requires TLS and grants `s3:GetObject` to the CloudFront service principal alone, scoped to the one distribution through Origin Access Control. CloudFront redirects HTTP to HTTPS, requires TLS 1.2, and sets a content security policy limited to the portal's own files, Google Identity Services (`accounts.google.com/gsi`) and the accounts API origin, with `frame-ancestors 'none'`, HSTS, `nosniff`, a strict referrer policy and a restrictive permissions policy. The publisher is one Lambda role (`anthus-one-portal-publish`) that can write only the portal bucket and read the CDK asset bucket; its `cloudfront:CreateInvalidation` is account-wide because CDK cannot scope it. The portal bundle must hold only public values (client IDs, API URLs). The hosting is committed disabled until a reviewed change enables it; see [accounts/ANTHUS_ONE_PORTAL.md](accounts/ANTHUS_ONE_PORTAL.md#hosting).

### Cognito

Self sign-up is disabled. The CRM and Cyclotron browser clients support only the Google identity provider; the password, SRP, custom and client-credentials flows are off, implicit grant is off, authorization code is on, and token revocation is enabled. Access and ID tokens last one hour and refresh tokens 30 days. The pool has deletion protection and a retain removal policy.

### Anthus One: Google directly, no Cognito

Anthus One has no user pool, domain, app client or identity provider. The browser obtains a Google ID token with Google Identity Services and sends it to the portal's own accounts API; see [ARCHITECTURE.md](ARCHITECTURE.md#anthus-one-sign-in-google-directly). Nothing server-side uses the Anthus One Google client secret (see [Google sign-in secret](#google-sign-in-secret)).

Google-direct evidence, verified identically by the BFF and central Accounts (`accounts/google-direct.ts`): RS256 signature against Google's published keys (`https://www.googleapis.com/oauth2/v3/certs`, cached for the lifetime Google states, at least 5 minutes and at most 24 hours, refetched at most once a minute for an unknown key ID, at most 10 keys and 64 KB; if Google cannot be reached the attempt is recorded and not repeated for 30 seconds, and the last good keys keep serving for at most 6 hours past their stated lifetime before verification fails closed); no `jku`, `jwk`, `x5u`, `x5c` or `crit`; `iss` equal to `https://accounts.google.com` or `accounts.google.com`; `aud` a single string equal to the registered client (an audience list is refused) and `azp`, if present, equal to it; `exp` in the future, `iat` at most 30 seconds ahead, `nbf` honored, lifetime at most 2 hours; `email_verified` the boolean `true`; a bounded printable `sub`; and a nonce of 16 to 256 URL-safe characters. Email is checked for verification but never selects a Person or grants anything.

Invariants of [Identity evidence](#identity-evidence) that change, compared with the Cognito path (for Ryan and security review):

Throttling on the portal API (no WAF; it has a monthly cost that is not approved): `POST /api/saas/{proxy+}` (account creation and enrollment) 2 per second, burst 5; the public `POST /identity/login-challenge` 2 per second, burst 5; every other route 10 per second, burst 20. The public challenge serves first sign-in only (token renewal uses the authenticated challenge), so 2 per second allows about 120 people to start signing in each minute, shared by all callers; it stores nothing, so exhausting it creates no data, and the sign-in page then says sign-in is unavailable and offers a retry.

Account creation is also capped in the central service: one Person may create at most 3 accounts per product (`accountCreationLimits` in `accounts/deployment.json`). The fourth returns `409 account_limit` ("contact us"), which keeps any one sign-in from growing the account set that every listing scans (more than 256 accounts makes listings fail with `503 account_read_budget` under the `scan` lookup). The check counts accounts the Person created through that product, finds them through the same discovery as listings, and ignores a replay of an existing request key. Concurrent creates can briefly exceed the cap by the number of simultaneous requests; the route throttle bounds that.

Residual risks to review: the ID token is kept in `sessionStorage` for up to an hour (as the CRM keeps its access token), so script injection into `one.anth.us` exposes it; Google's JWKS is fetched at runtime from the internet by two Lambdas, so an outage degrades sign-in to `401` until the cached keys are fetched; a stolen unexpired token can read that person's own accounts and create an empty account until it expires.

### Google sign-in secret

The Google OAuth client ID and secret come from the AWS Secrets Manager secret `prospectus/proof/oauth/google`, read by the CDK stack in `infra/lib/prospectus-backend.ts`. This secret is live in the papyrus-production account and is the one Prospectus uses. A copy that existed in the cyclotron-production account was unused and has since been deleted; because nothing referenced it, the deletion is not a deploy risk. Do not copy the secret into the repository, a pipeline variable or a log. Each Papyrus site has its own Google project and OAuth client for its own sign-in; Prospectus does not hold those.

Anthus One's Google OAuth client (`712526614578-dp3o0ofrukf7h2qcjst345t033mi990c.apps.googleusercontent.com`) needs no secret in this design: the ID token flow uses only the public client ID, and the tokens are verified with Google's published keys. The Secrets Manager secret `anthus-one/oauth/google` is referenced by no code, template or role and can be deleted. A Cognito pool (not used) or a server-side authorization-code exchange (not built) would be what needed it.

## Account authorization rules

- Every account read and write checks the caller's active membership, role, the product's registered capability and the account's entitlement for that product. Knowing a Person or account ID grants nothing.
- Viewers and revoked members cannot write. Writes by unsupported products and by unknown or pending Persons are refused before any canonical mutation.
- Concurrent membership changes use revision compare-and-set on the whole account document and recheck the actor. The last owner cannot be removed and a revoked actor cannot publish a stale change.
- Owners and admins with account-scoped `members:read` see an account's membership list; members and viewers see only their own membership.
- Apps own permissions on their own objects, keyed by Prospectus person and account IDs, and never exceed the Prospectus role. Cross-app roles are added to Prospectus.
- Product entitlements are changed only by reviewed operators, not by account owners.
- Request JSON cannot supply a grant, identity or role. Unknown fields are rejected.

### Cyclotron lab verifier

The Cyclotron lab BFF receives a Papyrus editor's Cognito access token from a Papyrus site and may ask Prospectus only who the token holder is and whether that person may act on an account. It does so as `arn:aws:iam::682849160744:role/cyclotron-lab-verifier`, a role in the Cyclotron account that only `cyclotron-console-bff-runtime` may assume. The registration is `accounts/lab-verifier.json`, committed disabled until a reviewed change enables it, and it is not a product with an issuer of its own.

- **Accepted tokens.** The token's `iss` and `client_id` must equal a site in `accounts/papyrus-sites.json`, the same registry the Papyrus sites use; the verifier holds no issuer or client list. That site's registration then verifies the signature, expiry, token use and login session. Tokens from the CRM pool, the Cyclotron console pool, Google (Anthus One), unregistered pools, unregistered clients and ID tokens fail with the same `401 invalid_human` as a forged token, so the response reveals nothing about what is registered.
- **Routes.** Exactly the two execution-authority routes. Every other path or method is refused with `403 verifier_route_forbidden` before any identity or account read. The REST API resource policy has one Allow for the role and exactly `GET /v1/identities/me` and `POST /v1/accounts/*/authorize`; the single Deny for every other principal lists the role as one more exemption.
- **Authority.** The Papyrus token proves identity only. `authorize` is evaluated as product `cyclotron`: the account must hold an active `cyclotron` entitlement that includes the operation, and the person must hold an active membership whose role permits it. A Papyrus site's own entitlement is neither required nor sufficient. The verifier's capabilities are `console:read` and `console:write`, intersected with the matched site's capabilities; `members:read` and `members:write` are never available, so owners and admins gain nothing beyond `console:*`, and viewers get `console:read` only. The answer is the existing point-in-time `authorize` result (account, person, product `cyclotron`, role, operation, revision).
- **No enumeration.** `identities/me` returns only the token holder's own Person, or `null` when that person never enrolled at the site. `authorize` answers a missing account, a non-member, a revoked member, a missing or disabled `cyclotron` entitlement and a Papyrus-only account with one identical `403 forbidden`. The verifier cannot list or read accounts, memberships, the directory or operator routes, and request JSON cannot name a person.
- **Registry safety.** Role names stay unique across every registration, the verifier included; the verifier must trust only registered, enabled, Google-only Papyrus sites exactly as reviewed; a mismatch stops the central Lambda before it serves requests. The lab's own account decides who may assume the role; the lab must still check that the authorized account equals its `X-Cyclotron-Account` pin.

### Operator access

`accounts/operator-grants.json` is the deployment-owned list of operators allowed to read the whole central directory. Each grant names exactly one registered product, a Cognito issuer, the SHA-256 digest of the verified subject, the permission `accounts:admin:read`, and a reviewed approval ID. The raw subject and email are never stored in the public source. Grants are validated at startup and copied to prevent mutation. Email addresses and the CRM `admin` group are never permission sources. The canonical Person and a current, nonce-confirmed Google session must still resolve before any operator read, and the existing issuer, client, subject, nonce, authentication age and login-family checks still apply.

Operator access does not create a membership, enable a product, authorize CRM use or allow a mutation. The operator routes are read-only and return no-store responses. Removing a grant denies the operator's next request without editing any membership. Before adding a grant, have the operator confirm their exact Google profile privately, review the verified issuer and subject mapping, and record explicit approval to read all accounts, entitlements and memberships. Never infer the operator from an email address or CRM role.

## Identity evidence

Central verification of Google-backed sign-in requires, for both the access and ID token: RS256 signature against the registered issuer's keys, exact `iss`, token purpose, `exp`, `iat` and `nbf`; ID `aud` equal to access `client_id` and to the single registered federation client; matching pool `sub`, `auth_time` and a non-empty `origin_jti`; authentication at most 300 seconds old and future skew at most 30 seconds; the ID nonce matching the unexpired challenge. The ID token must contain exactly one identity whose provider is the built-in Google provider with a bounded case-sensitive `userId`. Array order, `primary`, username and email never select the identity. Tokens are not logged or stored; challenge receipts keep only a digest of the token pair and the Person result.

A product registration with no `googleFederation` policy is denied the identity routes. The declaration is an operational approval input, not an inspection of AWS settings, so a reviewed policy ID must be re-reviewed when any of these change: the Google provider and client, Google-only client login, disabled alternative login paths, absence of linked profiles, administrator linking and pre-token customization, callback and logout URLs, and nonce, PKCE and state handling.

The pre-sign-in route `POST /api/saas/identity/login-challenge` is the only BFF route without a JWT authorizer. It requires the exact configured `Origin`, accepts only a 64-character lowercase hexadecimal `loginStateDigest`, reads no account data and is throttled by API Gateway (1 request per second, burst 2, for all callers together, so it can be exhausted; sign-in then falls back to a plain login). It stores nothing, so an attacker can create no durable data by calling it.

Login challenges are stateless signed tokens (`v1.<keyId>.<payload>.<mac>`). The signer is chosen by `loginChallengeSigner` in `accounts/deployment.json`:

- `parameter-store` (the Anthus deployment): HMAC-SHA-256 in the central Lambda with Node crypto. The secret is an SSM SecureString parameter (`<parameterPrefix><keyId>`, default `/prospectus/central-accounts/login-challenge-mac/v1`) encrypted with the AWS managed `aws/ssm` key, created by an operator and never by CDK or the repository. It is fetched with `GetParameter` and decryption, held in Lambda memory for at most 15 minutes, must decode to at least 32 bytes, and is never logged. MACs are compared with `crypto.timingSafeEqual`. The central runtime role gets exactly `ssm:GetParameter` on the configured parameter ARN(s) and no `kms:Decrypt`: the `aws/ssm` key policy already allows every principal in the account that SSM authorizes (`kms:ViaService = ssm.us-east-1.amazonaws.com`, `kms:CallerAccount` = this account).
- `kms`: one AWS KMS HMAC key (`HMAC_256`, `GENERATE_VERIFY_MAC`), created in CDK only when selected; the role gets `kms:GenerateMac` and `kms:VerifyMac` on that key ARN with `kms:MacAlgorithm = HMAC_SHA_256`.

The payload is a fixed-position JSON array (domain tag, challenge ID, nonce, `issuedAt`, `expiresAt`, login state digest, product, principal, issuer, client ID, policy revision), so key order and whitespace cannot vary, and the MAC covers the exact payload bytes. The key ID in the token (`^[a-z0-9]{1,16}$`) selects the secret; only the configured current and previous key IDs are accepted, and any other ID is rejected without reading a secret. Verification runs before the payload is interpreted and only after the caller and both Cognito tokens have verified. Expiry (300 seconds), nonce equality with the ID token, binding and login state are then checked exactly as for a stored challenge.

- Token theft: a token is useless without a fresh ID token carrying its nonce, Cognito login time within 300 seconds, a matching binding and, for the pre-sign-in path, the raw login state whose digest it carries. The browser keeps it in `sessionStorage` next to the nonce and state it already keeps.
- Replay: the first successful resolve creates the login receipt at `logins/<challengeId>.json` (a conditional create with the existing operation identity, made before any read of an absent key). The same evidence returns the same Person; changed evidence returns `409 challenge_replay`. After expiry the existing freshness rules reject it.
- Secret exposure (parameter-store): the secret lives in Lambda memory for the cache period, so code execution in the central Lambda or `ssm:GetParameter` on the parameter reveals it, and with it the ability to forge challenges (not sign-ins: forgery still needs a valid Cognito ID token with the matching nonce, binding and login time). A KMS key would keep the key material outside the Lambda. The parameter is readable only by the central runtime role, plus account administrators, and CloudTrail records each `GetParameter`.
- Rotation: put a new parameter version name (`v2`), set `currentKeyId` to `v2` and `previousKeyId` to `v1`, deploy, and remove `previousKeyId` after more than 300 seconds. Tokens in flight keep verifying; the cache means a changed secret under the same name takes effect within 15 minutes.
- Outage: a missing, unreadable, short or malformed secret, or an SSM or KMS failure at issue, returns `503` and the browser falls back to a plain sign-in. At resolve it returns `503` and the retry rule applies. Invalid MACs and malformed tokens return `401 challenge_invalid` and write nothing. Deploying before the parameter exists therefore degrades to plain sign-in, not an outage.
- Rollout: stored challenges issued before the change still resolve by `challengeId`; with no signer configured the service issues stored challenges as before.

### Public-reader site subjects

A public-reader site (`"audience": "public-reader"`, today `papyrus-shipped`) never receives the global Person ID. Everything it is told about a person is one pairwise subject, in the style of an OpenID Connect pairwise `sub`:

```
siteSubject = "ss1_" + base64url(HMAC-SHA-256(secret_v1, "prospectus-site-subject:v1\n" + product + "\n" + personId))
```

unpadded, so it always matches `^ss1_[A-Za-z0-9_-]{43}$`. The product is the reader's registered product name, taken from the verified IAM caller, never from the request. Without the secret, subjects on two sites cannot be linked to each other or to the Person ID, and a site cannot compute any other site's subject.

- **One gate.** `publicReaderHandler` (`accounts/site-subjects.ts`) wraps the whole central composition. For a reader caller it loads the secret first, then rewrites the response: `person` becomes `{ "siteSubject": … }` (or `null`), a successful body may carry only the keys listed for its route, account lists must be empty, errors keep only their fixed `error` and `message`, and a final check refuses any body that still contains the Person ID or creation time. Anything unexpected becomes `503`. Editor sites, the CRM, Cyclotron, Anthus One and the lab verifier reach the inner handlers unchanged.
- **What is withheld.** The Person ID; `createdAt` (identical on every site, so it would link the subjects); the Google subject and Cognito subject; email (never stored as identity). Prospectus holds no display name, so a reader site gets none: it must ask its own reader for a public handle.
- **Fail closed.** No configured secret, a missing, unreadable, non-base64 or shorter than 32-byte parameter, or an SSM failure returns `503 identity_unavailable` to the reader site before any challenge, enrollment or lookup runs, and never a Person ID instead. Failed reads are not cached; a loaded secret is cached for the life of the Lambda instance, because it never changes under its name. Editor sites are unaffected by the secret.
- **Logs.** The central Lambda logs only storage timing records (operation, duration, success). Nothing on the reader path logs a body, a Person ID or a subject; the tests capture console output during reader calls and scan it.
- **Secret.** An SSM SecureString (`/prospectus/central-accounts/site-subject/v1`, `aws/ssm` key), 48 random bytes, base64. It is created once by a create-only CloudFormation custom resource (`Custom::ProspectusSiteSubjectSecret`, `infra/lib/site-subject-secret.ts`) whose Lambda generates the value itself and calls `PutParameter` with `Overwrite: false`; the value is never in the template, never returned to CloudFormation (`NoEcho`, no data) and never logged. Updates and stack deletion leave it untouched (the resource is retained). The initializer role may only `ssm:PutParameter` on that one ARN, with an explicit deny when `ssm:Overwrite` is `true`; the central runtime role gets only `ssm:GetParameter` on it. Anyone who can read the parameter (the central runtime, account administrators) can link every site's subjects to Person IDs; CloudTrail records each read.
- **No silent rotation.** Changing or deleting the v1 value changes every subject on every reader site, which is indistinguishable from every reader being deleted. The value is therefore never rotated. A new secret is a new version (`v2`, subjects `ss2_…`) introduced as an explicit migration: both versions are derived for a transition period and each site is given an `ss1_` to `ss2_` mapping before `v1` is retired. That migration is not built.
- **Retired subjects.** When a Person is deleted or merged, the future delete or merge operation calls `RetiredSiteSubjects.retirePerson` (`accounts/retired-site-subjects.ts`) with its operation ID, the Person, the reason, the surviving Person for a merge and the reader products the Person enrolled on. Each of those sites can then list its own retired subjects at `GET /v1/accounts/site-subjects/retired`, with the surviving subject on the same site for a merge. The record stores no Person ID. Its time is the start of the hour it was recorded in, and records within an hour are ordered by the site's own subject, so two sites cannot align their records by exact time or order; an hour is listed only after it has ended plus 60 seconds. Every other caller is refused with `403`. Prospectus does not yet delete or merge Persons, so nothing calls `retirePerson` today.

Error contract: `400` malformed input or raw authority fields, `401` invalid token, session or nonce or an expired challenge, `403` wrong caller, product, client or policy, `409` consumed challenge with changed proof or an identity mapping conflict, `429` capacity, `503` repository unavailable.

## Amplify rewrite helper

The remote CLI sign-in pages are served on prospectus.anth.us through one proxy rewrite that the backend owns (see [ARCHITECTURE.md](ARCHITECTURE.md#remote-cli-sign-in-cli-login)). Its custom resource Lambda `prospectus-cli-rewrite` runs only during CloudFormation changes. Its role `prospectus-cli-rewrite` may `amplify:GetApp` and `amplify:UpdateApp` on `arn:aws:amplify:us-east-1:712236451410:apps/d15sc1sptohtqb` and write its own log group, nothing else: no `iam:PassRole`, no branch, domain or other app. `UpdateApp` on that app could change any app setting, so the code is reviewed like a policy: it changes only `customRules`, and only the rule whose source is `/cli/<*>`.

## Newsletter token key

Newsletter confirmation and unsubscribe links are signed with HMAC-SHA-256 under the SSM SecureString `/prospectus/newsletter/token-signing/v1` (`aws/ssm` key), 48 random bytes, base64. Format and claims are in [ARCHITECTURE.md](ARCHITECTURE.md#newsletter-mailing-lists).

- **Created once, as code.** A create-only custom resource (`Custom::ProspectusNewsletterTokenKey`, Lambda `prospectus-newsletter-token-init`, the same initializer as the site subject secret with its own label) generates the value and calls `PutParameter` with `Overwrite: false`. The value is never in the template, never returned to CloudFormation (`NoEcho`, no data) and never logged; updates and stack deletion leave it untouched. Its role may only `ssm:PutParameter` on that one ARN, with an explicit deny when `ssm:Overwrite` is `true`. The intake runtime gets only `ssm:GetParameter` on it, and the runtime waits for the custom resource.
- **What a token grants.** A confirm token can activate one pending subscription for 7 days; an unsubscribe token can only unsubscribe one subscription, forever. Neither reveals the address, which is never in a link. Pages served for a `GET` change nothing, so link scanners cannot subscribe or unsubscribe anyone.
- **Fail closed.** A missing, short or unreadable key makes signing fail (the signup is still stored and answered 202, and no email is sent) and makes the pages answer 503 "try again" without changing anything. A loaded key is cached for the Lambda instance's life; failures are not cached.
- **No silent rotation.** Unsubscribe tokens never expire, so replacing the v1 value would break the unsubscribe link in every email already sent. A future `v2` must keep verifying `v1` tokens.

The SES sending identity `news.apyr.us` is separate from `apyr.us` and `p.apyr.us`, so list reputation and any DMARC failures stay on the subdomain. `ses:SendEmail` is limited to that identity and the `prospectus-newsletter` configuration set, and the `ses:FromAddress` condition pins the From address to the list sender.

## Billing

Billing is planned, not built; the model is [BILLING.md](BILLING.md). These rules apply from the first billing change.

- **No card data.** Prospectus never collects, receives or stores card or bank account numbers. Payment methods are collected by Stripe Checkout and managed in the Stripe customer portal; the portal only redirects to Stripe and loads no Stripe script. This keeps Prospectus within PCI SAQ A.
- **Billing contact data.** A billing profile holds the contact name, email, postal address and tax id the client supplied. It is billing data, not identity: it is never used to find, match or authorize a Person, and it is never logged. The CRM shows it masked until revealed, and the portal returns it masked. Billing follow-ups carry the account id and invoice number only. Billing contact data and invoices are financial records. Their retention period and deletion request procedure are open (kanbus-d7ec0e) and must be recorded here before any live mode.
- **Who may write.** Only holders of the reviewed operator permission `accounts:admin:billing` in `accounts/operator-grants.json` may set profiles, change lines, raise, issue and void invoices, record external payments, allocate, reverse and write off. There is no second-operator confirmation. `accounts:admin:read` sees billing read-only. Customers may only read their own account's billing, start Stripe Checkout and open the Stripe customer portal. The server enforces this on every route, for the CRM and the CLI alike. Billing never changes an entitlement; suspension is an operator action through the entitlement route.
- **Stripe parameters.** The restricted Stripe API key and the webhook signing secret are SSM SecureString parameters `/prospectus/billing/stripe/secret-key/v1` and `/prospectus/billing/stripe/webhook-secret/v1` (`aws/ssm` key), created by Ryan by hand and never by CDK, the repository, a pipeline variable, an issue or a log. Only the billing runtime role may `ssm:GetParameter` them. A missing or short parameter fails closed with `503 billing_unavailable`.
- **Webhook.** `POST /billing/stripe/webhook` is unauthenticated, so it trusts only Stripe's v1 signature, checked against the signing secret with a 300-second tolerance. Unsigned, tampered, stale, oversized and unknown events are refused with `400` and write nothing. Each event is journaled by its Stripe event id with an absent-only write, so a redelivery is a no-op, and events apply idempotently in any order. The route is throttled.
- **Least privilege.** The billing runtime role may read and write only `prospectus-central/billing/` and its control files and cannot read identities, accounts or intake prefixes. The accounts runtime cannot write billing. Every new billing role, route, parameter grant and operator grant needs Ryan's concrete approval before it is deployed.

## Data handling

- The S3 bucket is private, versioned, TLS only and retained on stack deletion. Releases never rewrite or delete canonical paths.
- The central accounts runtime role may `GetObject` and `PutObject` only under the four `prospectus-central/` scopes listed in [ARCHITECTURE.md](ARCHITECTURE.md#storage), plus bucket-level `s3:ListBucket` limited by a `StringLike s3:prefix` condition to those same four scopes. It has no delete, DynamoDB, Cognito management or deploy rights.
- The intake runtime may invoke only `prospectus-api` and read and write only the intake identity and receipt prefixes, plus, while a newsletter is enabled, the `intake-newsletter/` prefix, `ssm:GetParameter` on the newsletter token key and `ses:SendEmail` on the newsletter identity and configuration set with `ses:FromAddress` pinned to the list senders. It has no listing, deletion, catalog, Cognito, Secrets Manager or IAM rights, and request bodies and contact data are not logged; an unconfirmed submission logs only an error class and transport outcome. Intake claims are created first with an absent-only conditional write and read only when they already exist, so no listing right is needed.
- The Kanbus runtime role is limited to the CRM namespace prefixes and to catalog rows whose leading key is that namespace.
- Public-reader sites receive only pairwise site subjects; see [Public-reader site subjects](#public-reader-site-subjects). Retired-subject records under `identities/retired-subjects/` hold the product, the retired and surviving subjects, the reason and the hour, and no Person ID. They are kept so a site that polls late can still catch up.
- No persistent access keys exist. Runtime credentials come from Lambda roles.
- Server-only SigV4 code lives in `server/` and `@anthus/prospectus-accounts-client/server`; never import it into a browser bundle, and never forward an arbitrary browser token in place of a verified session.
- Real inquiry contacts are kept until the person asks for deletion (approved 2026-10-17 with privacy notice `contact-v1`). This covers the prospect, any `needs-review` prospect and every intake inbox item (`intake-receipts/` objects with `kind: "intake-inbox"`), which hold the full inquiry including name, email and message; a deletion request removes all of them. Inbox items add no access: they live in the prefix the intake role already reads and writes, and the operator refile script (`scripts/refile-intake-inbox.ts`) runs with the operator's own credentials, not the Lambda role. Logs for deferred filing carry reason codes only. Tests and previews use only made-up data and `.invalid` addresses.

## Known limits

- Local JWT verification does not consult Cognito revocation state, so central token-family revocation is not immediate. Sessions in each BFF must invalidate their own server session on logout, and production must choose revocation and maximum-session-age behavior explicitly.
- A compromised Cognito pool administrator can undermine its assertions.
- An identity execution claim interrupted before canonical publication stays denied until an operator reconciles it; no automatic reset exists because a late native S3 request could still arrive.
- Account discovery scans up to 256 account documents per request and fails with `503` beyond that. Larger installations need a designed index and pagination.
- Per-person account quota is not enforced. Audit entries are capped at 128 per account with no rollover.
- Identity enrollment is a recoverable multi-file protocol, not an atomic S3 transaction. Imports and edits to canonical identity files must be quiescent.
- A profile with several identities needs an explicit linking flow that does not exist; directory-backed legacy linking is denied.
- Intake uniqueness holds only among intake writers; manual creation and import do not take intake claims.
- Newsletter subscription records hold the address, the signup requests and the consent record, kept until the person asks for deletion (notice `papyrus-newsletter-v1`). A deletion request removes the subscription record and the prospect's `custom.newsletters` entry; the hashed suppression record holds no address and stays, so the unsubscribe is still honoured. Suppression hashes are unsalted SHA-256 over the workspace, list and address, so someone with bucket read access could test a guessed address against them; bucket access is already limited to the runtimes and administrators.
- SES bounce and complaint events are not stored in Prospectus: SES suppresses those addresses itself, and the operator export subtracts the SES suppression list. Subscription records therefore do not show a bounce or complaint.
- Tests cover process crashes and restarts, not disk or power loss or real S3 failure modes.
- Retired site subjects can still be correlated across colluding reader sites when a person enrolled on both and few retirements happen in the same hour. Listing reads every record path for the site (up to 5,000, then `503`); a high retirement volume needs time-sharded listing. Person deletion and merge themselves do not exist yet.

## Change control

New persistent IAM or security resources, OAuth client or callback changes, and new operator grants need concrete approval before they are deployed. The browser origins allowed to sign in to the CRM, call its API and post to its accounts service are exactly `APP_ORIGINS` in `infra/lib/scope.ts`: production and `http://localhost:5417` for `npm run dev:cloud`. The portal's origin, `https://one.anth.us`, is `PORTAL_ORIGINS`: it is the portal API's CORS and POST origin and the only Authorized JavaScript origin of the production Anthus One Google client. It is not a CRM callback, CORS or BFF origin, and there is no localhost origin on any production portal surface; local portal work uses a separate development Google client (kanbus-1b54c9). A localhost origin lets a developer's own machine complete sign-in; the authorization-code flow still requires PKCE and matching state, and no token reaches any other host. Pin Kanbus and Virtuus revisions; never deploy from a moving dependency branch.
