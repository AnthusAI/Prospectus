# Security

The repository is public and MIT licensed; the deployed CRM and account service are private. Never commit real customer records, credentials, tokens, subjects or email addresses of real people. Keep deployment credentials in the approved platform configuration.

## Principals and authentication

| Surface                                                | Who can call                                        | How it is checked                                                                                                                                                          |
| ------------------------------------------------------ | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CRM Kanbus API (`/api/{proxy+}`)                       | Invited staff                                       | Cognito JWT from the Google-only browser client, then membership in the `prospectus-members` group                                                                         |
| Accounts BFF (`/api/saas/*`)                           | Any signed-in person                                | Same JWT authorizer; the BFF verifies the token again and signs central requests itself                                                                                    |
| Anthus One accounts API (`anthus-one` HTTP API)        | A person signed in with Google at `one.anth.us`     | Google ID token (authorizer: issuer and audience), verified again by the BFF and by central Accounts; customer routes only, never operator routes                          |
| Central accounts service                               | Registered product roles only                       | IAM SigV4, an API Gateway resource policy that allows each named role only its routes, and a deny for every other principal                                                |
| Inquiry intake (`POST /intake/demo`)                   | The public, from allowed origins                    | Origin and notice checks, throttling and a fixed intake actor; no read access                                                                                              |
| App waitlist intake (`POST /intake/waitlist/<formId>`) | The public, from the origins declared for that form | Per-form origin binding, per-form notice version, strict attribute allowlist, a route-level throttle and a fixed intake actor; no read access, no accounts or entitlements |

Signing in alone grants no CRM staff access, no account membership and no product entitlement.

### Anthus One hosting

`one.anth.us` is a public static site, so it holds no data: its bucket contains only the built portal bundle. The bucket blocks all public access, requires TLS and grants `s3:GetObject` to the CloudFront service principal alone, scoped to the one distribution through Origin Access Control. CloudFront redirects HTTP to HTTPS, requires TLS 1.2, and sets a content security policy limited to the portal's own files, Google Identity Services (`accounts.google.com/gsi`) and the accounts API origin, with `frame-ancestors 'none'`, HSTS, `nosniff`, a strict referrer policy and a restrictive permissions policy. The publisher is one Lambda role (`anthus-one-portal-publish`) that can write only the portal bucket and read the CDK asset bucket; its `cloudfront:CreateInvalidation` is account-wide because CDK cannot scope it. The portal bundle must hold only public values (client IDs, API URLs). The hosting is committed disabled until a reviewed change enables it; see [accounts/ANTHUS_ONE_PORTAL.md](accounts/ANTHUS_ONE_PORTAL.md#hosting).

### Cognito

Self sign-up is disabled. The CRM and Cyclotron browser clients support only the Google identity provider; the password, SRP, custom and client-credentials flows are off, implicit grant is off, authorization code is on, and token revocation is enabled. Access and ID tokens last one hour and refresh tokens 30 days. The pool has deletion protection and a retain removal policy.

### Anthus One: Google directly, no Cognito

Anthus One has no user pool, domain, app client or identity provider. The browser obtains a Google ID token with Google Identity Services and sends it to the portal's own accounts API; see [ARCHITECTURE.md](ARCHITECTURE.md#anthus-one-sign-in-google-directly). Nothing server-side uses the Anthus One Google client secret (see [Google sign-in secret](#google-sign-in-secret)).

Google-direct evidence, verified identically by the BFF and central Accounts (`accounts/google-direct.ts`): RS256 signature against Google's published keys (`https://www.googleapis.com/oauth2/v3/certs`, cached for the lifetime Google states, at least 5 minutes and at most 24 hours, refetched at most once a minute for an unknown key ID, at most 10 keys and 64 KB); no `jku`, `jwk`, `x5u`, `x5c` or `crit`; `iss` equal to `https://accounts.google.com` or `accounts.google.com`; `aud` a single string equal to the registered client (an audience list is refused) and `azp`, if present, equal to it; `exp` in the future, `iat` at most 30 seconds ahead, `nbf` honored, lifetime at most 2 hours; `email_verified` the boolean `true`; a bounded printable `sub`; and a nonce of 16 to 256 URL-safe characters. Email is checked for verification but never selects a Person or grants anything.

Invariants of [Identity evidence](#identity-evidence) that change, compared with the Cognito path (for Ryan and security review):

| Cognito invariant                                                                                                 | Google-direct                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Access and ID token pair with matching `sub`, `auth_time`, `origin_jti` ("one login family")                      | Dropped. Google issues one ID token; there is no access token or login family. `iat` and a digest of the nonce stand in for `auth_time` and the lineage                                                                                                                           |
| `auth_time` at most 300 seconds old on every call                                                                 | Changed. Enrollment (`/identity/resolve`) requires `iat` at most 300 seconds old and an unexpired challenge. Ordinary calls accept any unexpired token (up to about an hour)                                                                                                      |
| ID nonce equals the unexpired challenge nonce                                                                     | Kept for enrollment. For ordinary calls the nonce must be present and well-formed, but cannot be matched to a challenge, because challenges live 300 seconds and tokens an hour. A stolen token is therefore a bearer credential until it expires, as with a Cognito access token |
| Session binding: `/identities/me` and directory reads require this exact enrolled login (`auth_time` and lineage) | Changed. They require an enrolled alias with this product's exact binding (product, role, issuer, client, policy revision), not a particular login. Any unexpired Google token for an enrolled subject works                                                                      |
| Login state digest binds the challenge to the browser that asked                                                  | Kept: the page sends `sha256(state)` with the challenge request and the raw `state` with the resolve                                                                                                                                                                              |
| Origin binding                                                                                                    | Kept for the BFF's POST routes (exact `Origin`, portal origins only); GIS itself only mints tokens for the Google client's Authorized JavaScript origins. GET routes are not origin checked, as for the CRM                                                                       |
| Pool boundary (Cognito issuer, app client, Google-only, no linked profiles, no admin linking)                     | Replaced by Google's own: the Anthus One OAuth client's Authorized JavaScript origins and consent screen. There is no pool to misconfigure or administer, so "A compromised Cognito pool administrator can undermine its assertions" does not apply to the portal                 |
| Exactly one linked Google identity in `identities`                                                                | Not applicable: the token's own `sub` is the Google subject                                                                                                                                                                                                                       |
| Token revocation and refresh tokens                                                                               | None. There is no refresh token: renewing needs GIS again. Revocation is Google's (account state, consent), checked only when a new token is issued                                                                                                                               |
| Cognito `cognito:groups` (CRM)                                                                                    | Not applicable. The portal credential is not accepted by the CRM API (its authorizer has a different issuer and audience) and the CRM's tokens are not accepted by the portal (issuer and audience differ)                                                                        |

The portal API's `POST /identity/login-challenge` is throttled like the CRM's (1 request per second, burst 2, shared by all callers). The sign-in page then says sign-in is unavailable and offers a retry.

Residual risks to review: the ID token is kept in `sessionStorage` for up to an hour (as the CRM keeps its access token), so script injection into `one.anth.us` exposes it; Google's JWKS is fetched at runtime from the internet by two Lambdas, so an outage degrades sign-in to `401` until the cached keys are fetched; a stolen unexpired token can read that person's own accounts and create an empty account until it expires.

### Google sign-in secret

The Google OAuth client ID and secret come from the AWS Secrets Manager secret `prospectus/proof/oauth/google`, read by the CDK stack in `infra/lib/prospectus-backend.ts`. This secret is live in the papyrus-production account and is the one Prospectus uses. A copy that existed in the cyclotron-production account was unused and has since been deleted; because nothing referenced it, the deletion is not a deploy risk. Do not copy the secret into the repository, a pipeline variable or a log. Each Papyrus site has its own Google project and OAuth client for its own sign-in; Prospectus does not hold those.

Anthus One's Google OAuth client (`712526614578-dp3o0ofrukf7h2qcjst345t033mi990c.apps.googleusercontent.com`) needs no secret in this design: the ID token flow uses only the public client ID, and the tokens are verified with Google's published keys. The Secrets Manager secret `anthus-one/oauth/google` is referenced by no code, template or role and can be deleted. A Cognito pool (not used) or a server-side authorization-code exchange (not built) would be what needed it.

## Account authorization rules

- Every account read and write checks the caller's active membership, role, the product's registered capability and the account's entitlement for that product. Knowing a Person or account ID grants nothing.
- Viewers and revoked members cannot write. Writes by unsupported products and by unknown or pending Persons are refused before any canonical mutation.
- Concurrent membership changes use revision compare-and-set on the whole account document and recheck the actor. The last owner cannot be removed and a revoked actor cannot publish a stale change.
- Owners and admins with account-scoped `members:read` see an account's membership list; members and viewers see only their own membership.
- Apps own permissions on their own objects, keyed by Prospectus person and account IDs, and never exceed the Prospectus role. Cross-app roles are added to Prospectus.
- Product entitlements are changed only by reviewed operators, not by account owners.
- Request JSON cannot supply a grant, identity or role. Unknown fields are rejected.

### Operator access

`accounts/operator-grants.json` is the deployment-owned list of operators allowed to read the whole central directory. Each grant names exactly one registered product, a Cognito issuer, the SHA-256 digest of the verified subject, the permission `accounts:admin:read`, and a reviewed approval ID. The raw subject and email are never stored in the public source. Grants are validated at startup and copied to prevent mutation. Email addresses and the CRM `admin` group are never permission sources. The canonical Person and a current, nonce-confirmed Google session must still resolve before any operator read, and the existing issuer, client, subject, nonce, authentication age and login-family checks still apply.

Operator access does not create a membership, enable a product, authorize CRM use or allow a mutation. The operator routes are read-only and return no-store responses. Removing a grant denies the operator's next request without editing any membership. Before adding a grant, have the operator confirm their exact Google profile privately, review the verified issuer and subject mapping, and record explicit approval to read all accounts, entitlements and memberships. Never infer the operator from an email address or CRM role.

## Identity evidence

Central verification of Google-backed sign-in requires, for both the access and ID token: RS256 signature against the registered issuer's keys, exact `iss`, token purpose, `exp`, `iat` and `nbf`; ID `aud` equal to access `client_id` and to the single registered federation client; matching pool `sub`, `auth_time` and a non-empty `origin_jti`; authentication at most 300 seconds old and future skew at most 30 seconds; the ID nonce matching the unexpired challenge. The ID token must contain exactly one identity whose provider is the built-in Google provider with a bounded case-sensitive `userId`. Array order, `primary`, username and email never select the identity. Tokens are not logged or stored; challenge receipts keep only a digest of the token pair and the Person result.

A product registration with no `googleFederation` policy is denied the identity routes. The declaration is an operational approval input, not an inspection of AWS settings, so a reviewed policy ID must be re-reviewed when any of these change: the Google provider and client, Google-only client login, disabled alternative login paths, absence of linked profiles, administrator linking and pre-token customization, callback and logout URLs, and nonce, PKCE and state handling.

The pre-sign-in route `POST /api/saas/identity/login-challenge` is the only BFF route without a JWT authorizer. It requires the exact configured `Origin`, accepts only a 64-character lowercase hexadecimal `loginStateDigest`, reads no account data and is throttled by API Gateway (1 request per second, burst 2, for all callers together, so it can be exhausted; sign-in then falls back to a plain login). It stores nothing, so an attacker can create no durable data by calling it.

Login challenges are stateless signed tokens (`v1.<keyId>.<payload>.<mac>`). The signer is chosen by `loginChallengeSigner` in `accounts/deployment.json`:

- `parameter-store` (the Anthus deployment): HMAC-SHA-256 in the central Lambda with Node crypto. The secret is an SSM SecureString parameter (`<parameterPrefix><keyId>`, default `/prospectus/central-accounts/login-challenge-mac/v1`) encrypted with the AWS managed `aws/ssm` key, created by an operator and never by CDK or the repository. It is fetched with `GetParameter` and decryption, held in Lambda memory for at most 15 minutes, must decode to at least 32 bytes, and is never logged. MACs are compared with `crypto.timingSafeEqual`. The central runtime role gets exactly `ssm:GetParameter` on the configured parameter ARN(s) and no `kms:Decrypt`: the `aws/ssm` key policy already allows every principal in the account that SSM authorizes (`kms:ViaService = ssm.us-east-1.amazonaws.com`, `kms:CallerAccount` = this account).
- `kms`: one AWS KMS HMAC key (`HMAC_256`, `GENERATE_VERIFY_MAC`), created in CDK only when selected; the role gets `kms:GenerateMac` and `kms:VerifyMac` on that key ARN with `kms:MacAlgorithm = HMAC_SHA_256`.

The payload is a fixed-position JSON array (domain tag, challenge ID, nonce, `issuedAt`, `expiresAt`, login state digest, product, principal, issuer, client ID, policy revision), so key order and whitespace cannot vary, and the MAC covers the exact payload bytes. The key ID in the token (`^[a-z0-9]{1,16}$`) selects the secret; only the configured current and previous key IDs are accepted, and any other ID is rejected without reading a secret. Verification runs before the payload is interpreted and only after the caller and both Cognito tokens have verified. Expiry (300 seconds), nonce equality with the ID token, binding and login state are then checked exactly as for a stored challenge.

- Token theft: a token is useless without a fresh ID token carrying its nonce, Cognito login time within 300 seconds, a matching binding and, for the pre-sign-in path, the raw login state whose digest it carries. The browser keeps it in `sessionStorage` next to the nonce and state it already keeps.
- Replay: the first successful resolve creates the login receipt at `logins/<challengeId>.json` (a conditional create with the existing operation identity, made before any read of an absent key). The same evidence returns the same Person; changed evidence returns `409 challenge_replay`. After expiry the existing freshness rules reject it.
- Secret exposure (parameter-store): the secret lives in Lambda memory for the cache period, so code execution in the central Lambda or `ssm:GetParameter` on the parameter reveals it, and with it the ability to forge challenges (not sign-ins: forgery still needs a valid Cognito ID token with the matching nonce, binding and login time). A KMS key would keep the key material outside the Lambda. The parameter is readable only by the central runtime role, plus account administrators, and CloudTrail records each `GetParameter`.
- Rotation: put a new parameter version name (`v2`), set `currentKeyId` to `v2` and `previousKeyId` to `v1`, deploy, and remove `previousKeyId` after more than 300 seconds. Tokens in flight keep verifying; the cache means a changed secret under the same name takes effect within 15 minutes.
- Outage: a missing, unreadable, short or malformed secret, or an SSM or KMS failure at issue, returns `503` and the browser falls back to a plain sign-in. At resolve it returns `503` and the retry rule applies. Invalid MACs and malformed tokens return `401 challenge_invalid` and write nothing. Deploying before the parameter exists therefore degrades to plain sign-in, not an outage.
- Rollout: stored challenges issued before the change still resolve by `challengeId`; with no signer configured the service issues stored challenges as before.

Error contract: `400` malformed input or raw authority fields, `401` invalid token, session or nonce or an expired challenge, `403` wrong caller, product, client or policy, `409` consumed challenge with changed proof or an identity mapping conflict, `429` capacity, `503` repository unavailable.

## Data handling

- The S3 bucket is private, versioned, TLS only and retained on stack deletion. Releases never rewrite or delete canonical paths.
- The central accounts runtime role may `GetObject` and `PutObject` only under the four `prospectus-central/` scopes listed in [ARCHITECTURE.md](ARCHITECTURE.md#storage), plus bucket-level `s3:ListBucket` limited by a `StringLike s3:prefix` condition to those same four scopes. It has no delete, DynamoDB, Cognito management or deploy rights.
- The intake runtime may invoke only `prospectus-api` and read and write only the intake identity and receipt prefixes. It has no listing, deletion, catalog, Cognito, Secrets Manager or IAM rights, and request bodies and contact data are not logged; an unconfirmed submission logs only an error class and transport outcome. Intake claims are created first with an absent-only conditional write and read only when they already exist, so no listing right is needed.
- The Kanbus runtime role is limited to the CRM namespace prefixes and to catalog rows whose leading key is that namespace.
- No persistent access keys exist. Runtime credentials come from Lambda roles.
- Server-only SigV4 code lives in `server/` and `@anthus/prospectus-accounts-client/server`; never import it into a browser bundle, and never forward an arbitrary browser token in place of a verified session.
- Real inquiry contacts are kept until the person asks for deletion (approved 2026-10-17 with privacy notice `contact-v1`). This covers the prospect, any `needs-review` prospect and every intake inbox item (`intake-receipts/` objects with `kind: "intake-inbox"`), which hold the full inquiry including name, email and message; a deletion request removes all of them. Inbox items add no access: they live in the prefix the intake role already reads and writes, and the operator refile script (`scripts/refile-intake-inbox.ts`) runs with the operator's own credentials, not the Lambda role. Logs for deferred filing carry reason codes only. Tests and previews use only made-up data and `.invalid` addresses.

## Known limits

- Local JWT verification does not consult Cognito revocation state, so central token-family revocation is not immediate. Sessions in each BFF must invalidate their own server session on logout, and production must choose revocation and maximum-session-age behavior explicitly.
- A compromised Cognito pool administrator can undermine its assertions.
- An identity execution claim interrupted before canonical publication stays denied until an operator reconciles it; no automatic reset exists because a late native S3 request could still arrive.
- Account discovery scans up to 256 account documents per request and fails with `503` beyond that. Larger installations need a designed index and pagination.
- Per-person account quota is not enforced. Audit entries are capped at 128 per account with no rollover.
- Identity enrollment is a recoverable multi-file protocol, not an atomic S3 transaction. Imports and edits to canonical identity files must be quiescent.
- A profile with several identities needs an explicit linking flow that does not exist; directory-backed legacy linking is denied.
- Intake uniqueness holds only among intake writers; manual creation and import do not take intake claims.
- Tests cover process crashes and restarts, not disk or power loss or real S3 failure modes.

## Change control

New persistent IAM or security resources, OAuth client or callback changes, and new operator grants need concrete approval before they are deployed. The browser origins allowed to sign in to the CRM, call its API and post to its accounts service are exactly `APP_ORIGINS` in `infra/lib/scope.ts`: production and `http://localhost:5417` for `npm run dev:cloud`. The portal's origins, `https://one.anth.us` and `http://localhost:5421`, are `PORTAL_ORIGINS`: they are the portal API's CORS and POST origins and the Anthus One Google client's Authorized JavaScript origins, and are not CRM callbacks, CORS or BFF origins. A localhost origin lets a developer's own machine complete sign-in; the authorization-code flow still requires PKCE and matching state, and no token reaches any other host. Pin Kanbus and Virtuus revisions; never deploy from a moving dependency branch.
